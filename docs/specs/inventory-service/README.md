## 2. 系統／服務定位

### 2.1 Problem & Goal

抽獎的熱門獎品會在活動開放的瞬間被大量併發請求擊中。核心不變量是：**無論多少併發，實際發放的實體獎品數絕不能超過庫存**（`FR-INV-02`）。這需要同時滿足兩件事：**低延遲**（併發判定「還有沒有貨」要快）與**不超抽**（出貨扣減的真相必須精確、不可扣成負數）。

inventory-service 是「**庫存真相來源 (source of truth)**」的承載者：它以**兩層**架構同時滿足「低延遲」與「不超抽」——一層是**即時判定層**（低延遲確認「還有沒有貨」，可暫時不精確），一層是**出貨真相層**（實際扣減、補償判定，必須精確）。本服務回答「**系統要提供什麼庫存行為**」，並以業務語意約束「結果如何才算符合目的」。

> **定位關鍵**：本服務是**純後端協作服務**，無使用者直接互動介面。它不決定抽獎結果、不決定降級，只決定「庫存扣減的真相」——誰能扣、扣多少、扣失敗了怎麼辦、如何收斂回真相。

### 2.2 Actors & User Roles

inventory-service **無 end-user（USER/ADMIN）actor**；其互動對象皆為系統內協作者：

| Role | 說明 | 主要互動 |
|------|------|----------|
| **campaign-service**（系統協作者） | 抽獎路徑上游 | 抽獎命中時確認庫存、取得確認結果；中獎後通知本服務扣減 |
| **扣減通知通道** | 通知傳遞介質 | 投遞扣減通知（可能重複投遞） |
| **帳目校對排程** | 系統內部排程觸發者 | 觸發定期校對（校正即時判定層、回收超時未完成的扣減） |
| **OPS（營運人員）** | 異常的被動接收者 | 接收補償告警（`FR-INV-03`、`NFR-06`），不直接操作本服務 |

> 權限語意：inventory-service **不信任任何 client**，亦無 client 可直接呼叫之狀態變更介面。一切庫存變更只能由「上游通知」或「內部排程」觸發。campaign-service 的呼叫身分由架構約定（內部服務信任），非使用者 RBAC。

### 2.3 Business Capabilities（本服務提供的能力）

1. 收到扣減通知後執行**庫存扣減**（真相扣減）
2. **冪等去重**（同一筆中獎只扣一次）
3. **補償**（扣減發現庫存不足時：撤銷中獎 + 校正即時判定層 + 告警）
4. **定期帳目校對**（以出貨真相校正即時判定層、回收超時未完成的扣減）— Should

> 註：抽獎路徑的「庫存確認」由 **campaign-service** 於抽獎時執行（`FR-CAMP-18`），本服務不承擔確認決策；本服務只在其後依扣減通知把扣減寫入出貨真相。

### UC-1 收到扣減通知並執行庫存扣減

- **Actor:** inventory-service 的扣減處理程序（通知來源：campaign-service 的扣減通知）
- **Precondition:** campaign-service 已抽中獎品、完成庫存確認並發出扣減通知（含抽獎記錄識別、獎品識別、數量）；通知已送達。
- **Main flow:**
  1. 處理程序接收扣減通知。
  2. 以抽獎記錄識別做冪等檢查：若已處理過 → 直接確認，不重複扣減；若未處理 → 繼續。
  3. 執行**庫存扣減**，條件為「剩餘庫存 > 0」。
  4. 扣減成功 → 將該筆扣減標記為「已完成」，確認通知。
  5. 扣減發現庫存不足 → 進入補償流程（UC-2），不落入正常扣減，並依錯誤流程處理（`FR-X-01`）。
- **Business rule:**
  - **出貨真相是庫存唯一真相來源**；抽獎時的庫存確認只是即時判定層，可隨時由出貨真相重建。任何時刻問「到底剩幾件」，以出貨真相為準。
  - 庫存扣減的「剩餘 > 0」條件是「**絕不超抽**」的最終保證：即使即時判定層誤判有貨，扣減也會失敗而非扣成負數。
  - 扣減語意：每筆通知扣減 `quantity` 件（本系統中每次抽獎 `quantity = 1`）。
  - 處理程序 **冪等**：相同抽獎記錄只扣減一次；通知重複投遞不造成重複扣減。
  - 扣減為**非同步、最終一致**：client 收到中獎結果時，出貨真相可能尚未扣完（見 §4.2）。
- **Acceptance intent:**
  - 每筆合法通知使出貨真相準確扣減 `quantity`。
  - 相同抽獎記錄重複投遞不重複扣減。
  - 扣減發現庫存不足時絕不扣成負數，且觸發補償（UC-2）。
- **Traceability:** `FR-INV-01`, `FR-INV-02`, `FR-INV-04`, `FR-X-01`

### UC-2 補償（扣減發現庫存不足）

- **Actor:** inventory-service（補償邏輯，由 UC-1 的「庫存不足」結果觸發）
- **Precondition:** UC-1 的庫存扣減回報「庫存不足」（即時判定層與出貨真相不一致，或即時判定層資料遺失重建期間的誤判）。
- **Main flow:**
  1. 偵測到扣減發現庫存不足 → 判定為**異常扣減**。
  2. 記錄異常並**撤銷該次中獎結果**（將其標記為「已撤銷」，撤銷其「中獎」語意）。
  3. **校正即時判定層**：將誤扣的確認額度加回（以出貨真相為準）。
  4. **發出告警**通知營運（OPS）。
  5. 後續以出貨真相為準收斂即時判定層（由帳目校對，UC-3）。
- **Business rule:**
  - **出貨真相為準**：真相說沒有就是沒有，不得因即時判定層誤判而超發。
  - 補償使「使用者看到的『中獎』結果被撤銷」——此為已接受的業務代價（詳見 §4.4 語意）。補償的產品規則（如發補償券）**超出本服務職責**；本服務只負責「撤銷 + 校正即時判定層 + 告警」。
  - 補償後即時判定層必須向出貨真相收斂：即時判定層只能被「加回」修正，**不得因此超於真相**。
  - 告警是異常的可觀察性出口（`NFR-06`）。
- **Acceptance intent:**
  - 庫存不足時不產生負庫存；該筆中獎被撤銷、即時判定層額度被加回、發出告警。
  - 補償後系統持續收斂至出貨真相。
- **Traceability:** `FR-INV-03`, `FR-X-01`

### UC-3 定期帳目校對 (Reconciliation)

- **Actor:** 排程帳目校對（系統內部，**Should** 優先級）
- **Precondition:** 活動進行中（或結束後清算）；即時判定層與出貨真相之間存在不一致窗口，或存在遺留未收尾的扣減。
- **Main flow:**
  1. 以 **出貨真相為基準**，校正即時判定層（將即時判定層對齊真相）。
  2. 掃描扣減記錄中**超過時限仍未完成**的記錄 → 回收其即時判定層額度（加回）。
  3. 記錄校對結果供稽核（audit log，屬可觀察性，非營運報表）。
- **Business rule:**
  - 校對是**收斂機制**（最終一致的收斂手段），**不改寫出貨真相**，只校正即時判定層與回收超時未完成的扣減。
  - 校正方向**單一**：即時判定層對齊真相，而非真相遷就即時判定層。
  - 屬 **Should** 優先級（prod 前完成），非 Must。
- **Acceptance intent:**
  - 校對後即時判定層與出貨真相一致（在正常收斂語意下）。
  - 超時未完成的扣減被回收，即時判定層額度不再被永久佔用。
- **Traceability:** `FR-INV-05`

## 4. Business State

### 4.1 庫存狀態模型 (Inventory State Model)

庫存狀態由**兩個層**構成，各自角色明確：

| 層 | 狀態 | 角色 | 一致性角色 |
|----|------|------|-----------|
| 即時判定層 | 剩餘可確認額度的鏡像 | 低延遲確認、併發判定「還有沒有貨」 | 可暫時不精確、可重建 |
| 出貨真相層 | 剩餘可出貨數量（真相） | 出貨扣減、補償判定 | 必須精確、不可超扣 |

> **語意**：兩者都是「剩餘庫存」的表示，但**出貨真相為唯一真相**。即時判定層是真相的近似鏡像，僅用於熱點路徑加速；它「少」可接受（可能把仍有貨誤判為沒貨，導致降級），「多」不允許（不可誤判有貨而超發）——這方向性由「先確認、後扣減」＋「扣減時再驗證剩餘」兜底共同保證。

### 4.2 不一致窗口語意 (Consistency Window Semantics)

```text
T0  campaign 確認庫存 50→49            (即時判定層，campaign-service 執行)
T1  campaign 記錄中獎結果              (上游)
T2  campaign 發出扣減通知 ──────────►  inventory-service
T3  inventory 扣減出貨真相 50→49       (真相層)
                  │
                  └── T0~T3 之間：即時判定層=49、出貨真相=50（不一致窗口）
```

- **不一致窗口大小** ≈ 通知延遲 + 處理時間（通常 ms ~ 秒級）。
- **方向性**：即時判定層只可能「比真相少」（確認先行），**不可能「比真相多」**——除非發生補償撤銷（UC-2）。此方向性保證「出貨真相」永不超扣。
- **可接受的理由**：抽獎是「短暫高併發、後台寫回」的場景，client 不需要即時看到「剩 N 件」的精確值；唯一不可妥協的是「實發 ≤ 出貨真相」，由「扣減時驗證剩餘」保證，與即時判定層的即時性無關。

### 4.3 扣減生命週期 (Deduction Lifecycle)

```text
已確認 ──► 已完成  (終態)
     │
     └────► 已撤銷   (終態；庫存不足補償 or 超時回收)
```

| 狀態 | 業務意義 | 進入條件 |
|------|----------|----------|
| 已確認 | 庫存已確認（campaign-service 已於即時判定層確認），等待扣減通知 | campaign-service 抽獎命中並確認成功 |
| 已完成 | 扣減通知已處理，出貨真相已扣減 | UC-1 扣減成功 |
| 已撤銷 | 補償撤銷（庫存不足）或超時回收，即時判定層額度加回 | UC-2（庫存不足）或 UC-3（超時回收） |

### 4.4 業務語意問題（AGENTS.md §3 要求回答）

1. **狀態能否回轉？**
   - 出貨真相**扣減**為單向（每次中獎只扣減），正常業務流程中不可加回。「加回」有兩條路徑：(a) 補償修正（已撤銷，UC-2），屬異常回滾；(b) 獎品 `quantity` 增加的差值同步（ADR-010），屬營運配置調整、非回轉。
   - 扣減生命週期：已確認 → 已完成 單向；已確認 → 已撤銷 單向（補償／超時）。已完成與已撤銷皆為終態，不可回轉、不可再扣減。

2. **使用者看到的是本系統狀態還是 upstream 狀態？**
   - inventory-service 的 **出貨真相是下游真相**；campaign-service 抽獎路徑看到的即時判定層，是「庫存確認層」的**可暫不精確**狀態（由 campaign-service 於抽獎時執行確認維護）。
   - end-user 不直接讀取庫存精確餘額——庫存精確餘額不即時暴露；使用者只感知「中獎／銘謝惠顧」的結果，其背後庫存由本服務與 campaign-service 協作決定。

3. **哪些角色能改狀態？**
   - **無任何使用者角色可直接改庫存**。出貨真相扣減由扣減通知觸發（UC-1）；即時判定層由 campaign-service 確認、本服務補償修正（UC-2）／帳目校對（UC-3）驅動；補償由異常路徑觸發。
   - OPS 僅被動接收告警，**不能直接改寫**庫存或扣減狀態。

4. **哪些欄位不能被使用者直接改？**
   - 庫存剩餘數（`stock`）：不得由 client／使用者直接設定，只能經**扣減**（UC-1）。
   - 即時判定層：只能由 campaign-service 確認／本服務補償／校對路徑修改，無對外寫入介面。
   - 抽獎記錄識別（冪等鍵）：由上游抽獎記錄決定（通知攜帶），處理程序 **不得自行生成**。

## 5. Business Data Dictionary

> 本表定義**欄位的業務意義**（SA 層）。型別、資料庫 schema、約束、索引屬 SD 之 Technical Data Dictionary，**不在本表定義**。

### 5.1 inventory（庫存）

| 欄位 | 業務意義 | 必填 | 合法值 | 真實來源 | 敏感性 |
|------|----------|------|--------|----------|--------|
| `prize_id` | 對應之獎品識別（與 campaign-service 獎品同一識別） | 是 | 有效獎品識別 | campaign-service 獎品配置（ADMIN 建立） | internal |

> **語意註記**：庫存真相的**初始值**來自 campaign-service 的獎品配置（`FR-CAMP-02` 的 `quantity`），inventory-service 以其為初始真相；此後一切扣減與剩餘數以本服務為準。初始值與後續 `quantity` 修改的同步機制見 **ADR-010**（事件驅動、差值調整、下限 guard）。

### 5.2 扣減記錄 (deductions)

| 欄位 | 業務意義 | 必填 | 合法值 | 真實來源 | 敏感性 |
|------|----------|------|--------|----------|--------|
| `draw_record_id` | 抽獎記錄識別；冪等去重鍵（每筆中獎唯一） | 是 | 唯一、對應一筆上游抽獎記錄 | campaign-service 發出之扣減通知 | internal |
| `prize_id` | 扣減之獎品 | 是 | 有效獎品識別 | 通知攜帶 | internal |
| `quantity` | 扣減件數（本系統每次抽獎 `= 1`） | 是 | 正整數（= 1） | 通知攜帶 | internal |
| `status` | 扣減生命週期狀態 | 是 | 已確認 / 已完成 / 已撤銷 | inventory-service 狀態機（§4.3） | internal |
| 確認時間 | 庫存確認發生的時間；超時回收之基準 | 是 | 合法時間 | inventory-service（確認時記錄） | internal |

> **語意註記**：`draw_record_id` 是扣減記錄的**冪等識別**（`FR-INV-04`）——同一 `draw_record_id` 對應至多一筆扣減記錄、至多一次出貨真相扣減；通知重複投遞撞此鍵即忽略。確認時間是「超時未完成」判定（`FR-INV-05`）的依據。

## 6. Acceptance Criteria

> 每條以 GIVEN/WHEN/THEN 描述，標註 AC ID 與對應 FR。

### 6.1 庫存扣減 (Deduction)

**AC-INV-001 — 扣減成功**（`FR-INV-01`, `FR-INV-02`）
- GIVEN 收到一筆扣減通知且出貨真相剩餘庫存 `> 0`
- WHEN 處理程序執行扣減
- THEN 出貨真相扣減 `quantity`、該扣減標記「已完成」、通知確認

**AC-INV-002 — 扣減發現庫存不足觸發補償**（`FR-INV-03`）
- GIVEN 出貨真相回報庫存不足
- WHEN 處理程序偵測到此結果
- THEN 執行補償：撤銷中獎結果、校正即時判定層（加回誤扣額度）、發出告警；庫存絕不為負

### 6.2 冪等 (Idempotency)

**AC-INV-003 — 冪等去重**（`FR-INV-04`）
- GIVEN 相同抽獎記錄的扣減通知被重複投遞
- WHEN 處理程序再次處理
- THEN 不重複扣減出貨真相、僅確認通知；該抽獎記錄對應的扣減僅發生一次

### 6.3 收斂與校對 (Convergence & Reconciliation)

**AC-INV-004 — 最終一致性收斂（正常收斂）**（`FR-INV-02`, `FR-INV-05`）
- GIVEN 一批扣減通知被處理且出貨真相扣減成功
- WHEN 帳目校對執行（以真相為準校正即時判定層）
- THEN 即時判定層收斂至出貨真相；不一致窗口內即時判定層 ≤ 真相，無超發

**AC-INV-005 — 校對回收超時扣減**（`FR-INV-05`）
- GIVEN 扣減記錄中存在超過時限仍未完成的記錄
- WHEN 帳目校對掃描
- THEN 回收其即時判定層額度（加回），使即時判定層額度不再被永久佔用

### 6.4 錯誤流程 (Error Flow)

**AC-INV-006 — 錯誤流程語意**（`FR-X-01`）
- GIVEN 處理程序遭遇通知格式不合法／重複投遞／庫存不足等錯誤情境
- WHEN 依各自情境處理
- THEN 重複投遞 → 冪等忽略；庫存不足 → 補償（UC-2）；格式不合法／不可處理 → 進入錯誤處理且無副作用；任何路徑都不造成負庫存、不重複扣減，並具可觀察性（log/alert）
