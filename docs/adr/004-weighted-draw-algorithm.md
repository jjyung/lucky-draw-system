# ADR-004: 權重隨機抽獎演算法 (Weighted Random Draw Algorithm)

**Date:** 2026-08-13
**Status:** Accepted

## Context

抽獎核心必須支援**動態獎品機率配置**：營運人員可以調整每個獎品的抽中機率，而不需要改 code。同時系統需要一個「什麼都沒抽到」的結果——README 中稱之為**銘謝惠顧（thank-you）**。

要處理的問題：

1. **機率模型**：如何從多個不同權重的獎品中做單次隨機選取，且保證總機率語意一致？
2. **銘謝惠顧的建模**：銘謝惠顧是一個「偽獎品」，還是特殊邏輯分支？
3. **機率驗證**：營運誤填機率（總和 ≠ 100%、負數、超過 100%）時，系統必須在**配置時間**就拒絕，而不是在抽獎執行時才出錯。

## Decision

採用 **權重隨機抽選（Weighted Random Selection）+ 累計機率區間（Cumulative Probability Intervals）** 演算法：

### 1. 銘謝惠顧建模為獎品

**銘謝惠顧是一個 type = `THANK_YOU` 的獎品**，與實體獎品（type = `PRIZE`）一樣存在 `prizes` table、一樣有機率欄位。好處是：

- 抽獎邏輯只需面對「一份獎品清單 + 一個隨機值」，不需要特殊 if-branch。
- 機率總和檢查天然涵蓋銘謝惠顧。

### 2. 機率語意：總和必須等於 100%

- 每個獎品有一個 `probability`（百分比，`double`），**含銘謝惠顧在內，所有獎品機率總和必須等於 100%**。
- 配置端（活動管理 API / admin UI）在建立或更新活動時**即時驗證**：
  - 每個 `probability` 介於 `(0, 100]`；
  - 總和與 100.0 的差值在浮點容差內（例如 `abs(sum - 100.0) <= 0.000001`）；
  - 至少存在一個 `THANK_YOU` 獎品（否則活動無法產生「沒中獎」結果）。
  - 驗證失敗 → 直接回傳 400/422，活動不落庫。

### 3. 選取演算法：單一隨機值走累計區間

```text
prizes = [p1(5%), p2(15%), p3(30%), THANK_YOU(50%)]

0      5     20     50     100
|--p1--|--p2--|--p3--|--TY--|

r = random double in [0, 100)
累計機率 running = 0
for prize in prizes (固定順序，按 id / 配置順序排序):
    running += prize.probability
    if r < running: return prize
throw IllegalStateException   // 理論上不可達（總和已驗證 = 100）
```

- 使用 **Java `ThreadLocalRandom` / `SecureRandom`** 產生單一個 `double` 落在 `[0, 100)`。
- 演算法為 **O(n)**，n = 獎品數，對每次抽獎而言成本可忽略。
- 排序需固定（例如依 `prize.id`），避免同一次活動內多次抽獎因集合順序不同導致結果不穩定。

### 4. 權重配置的儲存與快取

- 機率欄位存在 `prizes.probability`（見 ADR-002 campaign DB）。
- 活動啟動後，**抽獎用的獎品清單 + 機率**可緩存於 Redis / 本地 cache，抽獎時不每次查 DB；活動配置變更需要使快取失效或於下次活動週期生效。

## Consequences

**正面：**

- **營運零程式碼調整機率**：改 DB 配置即可調整中獎率，符合動態配置需求。
- **總和 100% 的強制語意**：銘謝惠顧視為獎品後，「沒有結果」不再是例外路徑，且機率合規性在配置時即被強制，營運錯誤不會進入 runtime。
- **演算法簡單可測**：單一 for-loop，可用單元測試驗證區間邊界（`r` 落在界線值）與統計分布（大量取樣趨近配置機率）。

**負面 / 需付出的代價：**

- **固定機率（static probability）**：此模型是每次抽獎獨立、機率不隨剩餘庫存動態調整。若未來需要「即時機率」（如庫存剩 1 件時中獎率陡升），需演化為動態權重模型（由 Redis 剩餘庫存計算權重），屬後續 ADR 範圍。
- **浮點比較**：機率總和驗證需小心處理浮點誤差，需定義明確容差。
- **配置一致性**：活動更新機率的同時若正在抽獎，需保證讀到一致快照（如 activity status + 版本號），避免「半套新機率」的混雜狀態。

## Alternatives

- **Alias Method (Vose)**：O(1) 選取、預處理 O(n)，適合「單一活動極高 QPS 且獎品清單固定」的場景；本系統每次抽獎前已有 Redis/DB 與鎖的開銷，O(n) 選取不是瓶頸，Alias Method 的複雜度不值得，保留為未來優化選項。
- **按機率產生多段區間整數（0-10000）後 mapping**：以整數避免浮點誤差，可作為實作細節選擇（`probability` 用 basis point / 萬分比），但演算法本質與本決策相同。
- **只對實體獎品抽、抽不到就銘謝惠顧（隱含機率 = 100% - 總和）**：看似簡潔，但會讓「銘謝惠顧機率」無法被營運明確配置與檢視，且總和語意不清（可能 > 100%），否決。
